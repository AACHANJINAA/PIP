시야 처리 병목 최적화 (Sector Grid)

Problem: 20만 마리의 NPC와 유저가 서로의 거리를 O(N^2)로 계산하여 서버 틱 심각한 저하 발생
Solution: 공간을 고정 크기의 Grid(Sector)로 분할하고 std::shared_mutex(Read-Write Lock)를 적용하여 인접 섹터의 객체만 탐색하도록 변경
Performance Gain:
탐색 복잡도를 O(K) (1<K<N) 수준으로 낮추어 서버 딜레이 20~30ms 시 동시 접속자 수 4400명 안정적 유지 (별개 네트워크에 속한 컴퓨터의 더미 클라이언트 사용)

네트워크 I/O 병목 및 데이터 파편화 최적화

Problem: 매 틱마다 쏟아지는 수많은 객체의 이동/투사체 패킷 전송(Send) 시스템 콜 비용 과다
Solution: 전송 큐에 패킷을 버퍼링 후 WSABUF 배열을 이용한 Scatter-Gather I/O(Batching)로 뭉쳐서 보내고, 수신단에서 링 버퍼 기반 재조립(Reassembly) 파서 구현
Performance Gain:
WSASend 시스템 콜 횟수 대폭 감소 및 패킷 유실률 제로 달성

DB  스레드 분리 및 Stored Procedure 설계 및 구현

Problem: 메인 워커 스레드에서 ODBC(동기식)로 DB에 쿼리를 전송할 경우, 응답이 올 때까지 IOCP 스레드가 정지(Blocking)되어 전체 서버의 응답 불능(Starvation)을 초래함.
Solution: DB 전담 스레드 분리 & Lock-Free Queue: 유저의 저장/불러오기 요청은 큐에 밀어넣고 워커 스레드는 즉각 복귀하여 패킷 처리를 이어갑니다.
Stored Procedure 도입: 복잡한 인벤토리, 퀘스트, 스킬 데이터 저장을 하나의 DB 프로시저로 묶어 네트워크 왕복 비용을 최소화하는것 뿐만 아니라 보안적으로 DB의 구조를 알 수 없도록 도입하였습니다.
Performance Gain:
워커 스레드의 I/O 블로킹 되지 않음 풀부하 상황에서도 패킷 처리 지연(Lag) 방지가 가능해집니다.
void db_thread_func() {
    while (true) {
        DbJob job;
        if (db_queue.try_pop(job)) { // Lock-Free Queue 기반 작업 인계
            if (job.type == SAVE_PLAYER) {
                // Stored Procedure 쿼리 실행으로 통신 비용 최소화
                std::string query = "EXEC sp_save_player " + std::to_string(job.uid);
                SQLExecDirect(hstmt, (SQLWCHAR*)query.c_str(), SQL_NTS);
            }
        }
    }
}

Lua Script를 활용한 확장성 있는 NPC AI

Problem: 20만 마리의 몬스터 패턴을 모두 C++로 하드코딩하기엔 한계가 있으며, 하나의 글로벌 lua_State를 사용하면 멀티스레드 환경에서 치명적인 Lock 병목이 발생합니다.
Solution:  thread_local 기반 Lua VM 할당: 각 IOCP 워커 스레드마다 고유의 독립적인 lua_State 풀을 유지합니다.
서로 다른 스레드가 동시에 C++에서 Lua 스크립트를 호출해도 상호 배제(Lock)가 전혀 필요 없습니다.
Performance Gain:
기획자가 직접 AI 로직(lua)을 수정할 수 있는 극대화된 확장성 확보 및 재컴파일 및 유지보수가 용이합니다
// npc_ai_manager.h 의 핵심 로직
static lua_State* get_state(int npc_type) {
    // thread_local 맵을 사용하여 스레드별로 안전하게 분리된 Lua State 반환
    thread_local std::unordered_map<int, lua_State*> pool;
    
    if (pool.find(npc_type) == pool.end()) {
        lua_State* L = luaL_newstate();
        luaL_openlibs(L);
        luaL_dofile(L, get_script_path(npc_type).c_str()); // 최초 1회 로드
        pool[npc_type] = L;
    }
    return pool[npc_type];
}

정밀 피격 동기화를 위한 지연 보상 (Rewind)

Problem: 네트워크 지연(Ping)으로 인해 클라이언트 화면의 몬스터 위치와 서버 위치가 달라 타격감 훼손
Solution: 모든 물리 객체의 최근 1초간 위치/히트박스 스냅샷을 원형 큐에 저장. 공격 패킷 타임스탬프 기반 과거 시간으로 Rewind 후 판정 처리
Performance Gain:
Ping 100ms 환경에서도 불일치 없는 완벽한 서버 권위형 피격 판정 달성

Behavior Tree(BT)를 활용한 보스 AI

Problem: 보스의 복잡한 페이즈 변화, 스킬 연계, 어그로 타겟 상실 등 다양한 예외 상황을 기존의 FSM(상태머신)으로 짜면 스파게티 코드가 되어 유령 포인터(Dangling Pointer) 및 서버 크래시를 유발함.
Solution: BT 모듈화 아키텍처: std::shared_ptr<BTNode> 기반의 트리 구조로 AI를 설계해 조건(Decorator)과 행동(Action)을 엄격히 분리했습니다.
빌더 패턴을 도입하여 트리 구조로 노드들을 붙일 수 있으며 블랙보드로 노드들의 공용데이터를 공유하도록 설계함
Performance Gain:
현재 상태 체크 시간 획기적 단축, 재사용 가능한 AI 노드 라이브러리 확보

Data Race가 없는 안전한 Room 아키텍처

Problem: 같은 인스턴스(Room)에 속한 몬스터와 유저들의 상태(HP, 위치)를 여러 워커 스레드가 동시에 수정하려 들면, 복잡한 Deadlock(교착상태)과 Data Race(데이터 오염)가 필연적으로 발생하고 이는 MO게임 기획 단계에서 없앨 수 있었습니다.
Solution: Job Queue 기반 로직 직렬화: 방(Room)마다 고유한 Command Queue를 부여하여 상태를 변경하는 모든 이벤트(공격, 이동, 버프)를 람다(Lambda)로 캡처해 Push 합니다.
한 번에 단 하나의 스레드만 해당 룸의 Job 큐를 비워냄으로써 로직이 순차적으로 실행됩니다.
Performance Gain:
객체별 Mutex Lock 오버헤드 완전 제거로 CPU 사이클을 절약하고, 데드락 구조를 원천 차단하여 초고속 전투 연산 달성 -> 물리엔진 루프에 알맞는 구조를 부가적으로 얻을수 있었습니다.
void PacketHandler::handle_attack(Session* session, AttackPacket* packet) {
    auto room = session->get_room();
    if (!room) return;
    // Data Race를 막기 위해 해당 룸의 전용 JobQueue로 로직을 밀어넣음
    room->PushJob([room, session, packet]() {
        // 이 블록 안의 코드는 오직 하나의 스레드에서만 안전하게 실행 보장!
        auto target = room->find_monster(packet->target_id);
        if (target) {
            target->take_damage(packet->damage);
        }
    });
}
