PIP Server Architecture

서버 아키텍쳐 전체적인 설계도입니다.

Behavior Tree(BT)를 활용한 보스 AI



Problem: 보스의 복잡한 페이즈(Phase) 변화, 스킬, 타겟팅 로직이 얽혀 스파게티 코드 가능성
Solution: 행동 트리(BT)의 Action 노드를 상속 구조로 모듈화하고, 타겟(유저) 상실 시 즉시 대응하는 예외처리(안전장치) 노드를 Decorator로 배치
Performance Gain: 보스 패턴 로직의 재사용성 확보

서버 물리 엔진(Jolt) 부하 억제 설계



Problem: 다수의 플레이어와 몬스터 객체 물리 연산을 서버가 모두 담당할 경우 심각한 물리 스레드 병목 발생
Solution: 대기 중인 NPC의 Motion Type을 Kinematic/Static(Sleep 상태)으로 설정하여 연산에서 제외하고, 교전 시 Dynamic으로 자동 승격(Dynamic Promotion)
Performance Gain: 충돌 연산 부하 최소화를 통한 안정적 서버 물리 프레임 타임 확보 (전체 CPU 사용량 84% -> 11%로 감소)

정밀 피격 동기화를 위한 지연 보상 (Rewind)




Problem: 네트워크 지연(Ping)으로 인해 클라이언트 화면의 몬스터 위치와 서버 위치가 달라 타격감 훼손
Solution: 모든 물리 객체의 최근 1초간 위치/히트박스 스냅샷을 원형 큐에 저장. 공격 패킷 타임스탬프 기반 과거 시간으로 Rewind 후 판정 처리
Performance Gain: Ping 100ms 환경에서도 불일치 없는 서버 피격 판정 달성

Data Race가 없는 안전한 Room(인스턴스 던전) 아키텍처



Problem: 한 방(Room)에 속한 객체 상태를 여러 워커 스레드가 동시 다발적으로 접근하여 수정하면 데이터 오염 및 데드락 위험
Solution: 방(Room)마다 고유한 Job Queue(명령 대기열)를 부여하여, 상태를 변경하는 모든 로직(이벤트)을 큐에 밀어넣고 단일 스레드 흐름으로 순차 처리(직렬화)
Performance Gain: 객체 단위의 동기화 락(Lock) 비용 완전 제거로 인해 서버 반응 속도 향상 및 데드락 100% 방지, MO RPG게임 특성 활용

DB 스레드 분리 및 Stored Procedure 설계

Problem: 멀티플레이 환경에서 인벤토리를 영속화해야 했지만, ODBC 표준 API는 동기 블로킹 방식. 워커 스레드는 방 하나의 플레이어·몬스터·Jolt 물리 Step을 통째로 굴리기 때문에, 쿼리 한 번이 수십 ms를 잡아먹으면 안됨. 그렇다고 DB 스레드에 컴포넌트 포인터를 그냥 넘기면 데이터 레이스 발생
Solution: DB 전담 1개 신설. 작업 단위인 DBTask는 페이로드를 std::any로 담아 타입을 소거 — 저장은 로직 스레드가 인벤토리를 값 복사한 스냅샷을 make_any로 이동시켜 넣고, 로드는 반대로. 요청 시점의 logic_thread_idx를 사용, DB 스레드는 완료 콜백을 그 인덱스의 로직 큐로만 되돌려주고 로직 워커 스레드에서 싱글스레드 알고리즘으로 처리
좋은 점: 로직 스레드는 즉시 리턴하므로 DB 지연이 게임 틱에 영향 없음, 완료 콜백이원래 소유 스레드에서 실행되므로 Player·InventoryComponent 접근에 Mutex가 하나도 필요 없습니다. std::any 덕분에 새 DB 작업(스탯 등)을 추가해도 DBTask 구조체와 큐는 그대로 두고 핸들러만 등록하면 되며, 연결 문자열을 "DUMMY"로 주면 SQL만 건너뛰고 큐·콜백 경로는 동일하게 타므로 팀원이 MSSQL 설치 없이 같은 비동기 코드 경로를 테스트할 수 있습니다.

시야 처리 병목 최적화 (Sector Grid)



Problem: 20만 마리의 NPC와 유저가 서로의 거리를 O(N^2)로 계산하여 서버 틱 심각한 저하 발생
Solution: 공간을 고정 크기의 Grid(Sector)로 분할하고 std::shared_mutex(Read-Write Lock)를 적용하여 인접 섹터의 객체만 탐색하도록 변경
Performance Gain: 탐색 복잡도를 O(k) 수준으로 낮추어 동시 접속자 수 4400명 안정적 유지

네트워크 I/O 병목 및 데이터 프래그멘테이션 최적화



Problem: 매 틱마다 쏟아지는 수많은 객체의 이동/투사체 패킷 전송(Send) 시스템 콜 비용 과다
Solution: 전송 큐에 패킷을 버퍼링 후 WSABUF 배열을 이용한 Scatter-Gather I/O(Batching)로 뭉쳐서 보내고, 수신단에서 링 버퍼 기반 재조립(Reassembly) 파서 구현
Performance Gain: WSASend 시스템 콜 횟수 대폭 감소 및 패킷 유실률 제로 달성

Lua Script를 활용한 확장성 있는 NPC AI

Problem: 20만 객체의 행동 패턴을 C++에 하드코딩하면 밸런스 한 줄을 고칠 때마다 재컴파일·재배포가 필요합니다. 그렇다고 Lua를 붙이면 lua_State가 재진입 불가라, 전역 하나를 공유하는 순간 모든 워커 스레드가 AI 호출마다 뮤텍스를 두고 경쟁해서 성능이 떨어집니다.
Solution: thread_local lua_State 풀을 두어 워커 스레드마다 독립적인 VM 7개를 보유하게 했습니다. 이를 가능하게 한 핵심 설계는 AI 스크립트를 순수 함수로 강제한 것입니다 — NPC의 모든 상태(HP·좌표·상태·타겟)는 C++가 소유하고 매 호출 ctx 테이블로 주입, 결과는 new_state·action으로만 반환받습니다. 보스 페이즈 전환과 크리퍼 자폭 카운트다운까지 이 왕복으로 처리해, lua_State를 상태 저장소가 아닌 순수 실행 엔진으로 만들었습니다. (저장,실행은 C++, 판단만 lua)
Result: AI 호출 시 락 획득 0회, lua_State 개수 = 스크립트 7종 × 코어 수 (16코어 기준 112개) — NPC가 20만이든 100만이든 불변 · NPC 이벤트를 IOCP로 아무 워커나 처리 — 스레드 핀닝·라우팅 로직 불필요, 부하 분산이 자동 · 한 스레드의 Lua 에러가 lua_pcall에 격리되어 다른 스레드로 전파되지 않음 · GC가 State 단위로 분산되어 전역 방식의 stop-the-world 정지가 없음 · 밸런스 수치는 npc_config.lua, 행동은 ai/*.lua로 분리

DataBase 서버 연동

Problem: 멀티플레이 게임에서 유저의 로그인 정보와 진행 상황(좌표·레벨·장비·인벤토리·퀘스트·스킬)을 영속화할 저장 시스템이 필요했습니다. 그런데 ODBC 표준 API는 동기 블로킹이라, IOCP 워커 스레드에서 직접 호출하면 쿼리가 끝날 때까지 그 스레드가 통째로 묶여 다른 유저의 패킷 처리까지 정지합니다. 로그인 한 번에 조회가 5번 필요한 구조라 접속이 몰리면 워커 풀이 전부 DB 대기로 빠지는 기아 상태가 발생합니다.

Solution: Windows가 ODBC 표준 API를 지원한다는 점을 활용해 MSSQL + Management Studio로 스키마와 저장 프로시저를 직접 설계하고, ODBC 핸들을 DB 전용 접근 스레드에 배치했습니다. 워커 스레드는 DBTask를 lock-free 큐에 던지고 즉시 복귀하며, 페이로드는 std::variant<monostate, string, player_data>로 담아 요청과 응답이 같은 객체로 왕복하게 했습니다. 완료 통지는 별도 채널을 만들지 않고 PostQueuedCompletionStatus로 IOCP에 되돌려, DB 결과가 일반 네트워크 I/O 완료와 동일한 경로로 배달되게 했습니다.

좋은 점: 메인 로직·I/O 스레드와 별개의 스레드에서 비동기로 연산이 처리되므로 DB가 아무리 느려도 게임 로직은 계속 돌아갑니다. 완료 통지에 IOCP를 재사용한 덕분에 콜백 큐·디스패처 없이 기존 io_type switch에 case 하나만 추가하면 됐습니다. 또한 모든 쿼리를 저장 프로시저로 캡슐화해 C++ 코드에 테이블·컬럼명이 전혀 노출되지 않고, 스키마가 바뀌어도 SP만 수정하면 서버 재컴파일이 불필요하며, DB 계정에 EXECUTE 권한만 부여할 수 있어 안전한 영속성 저장 체계를 만들었습니다. 종료 시에는 큐에 남은 작업을 모두 비우는 Drain 루프로 마지막 저장 유실도 막았습니다.
